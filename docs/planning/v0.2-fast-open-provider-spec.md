# Aviso v0.2 Fast And Open Provider Spec

Status: Current v0.2 requirement baseline / implementation candidate / release not ready
Updated: 2026-06-12

## Purpose

This document is the current v0.2 requirement baseline. It keeps the earliest v0.2 slice structure as historical planning, but the owner-confirmed requirements below are the current truth for docs-only execution, issue planning, and later validation threads.

This is not a release approval, live-provider validation record, Chrome Web Store approval record, or backend scope document.

## v0.2 Total Goal

Aviso v0.2 should make the product more open, faster, and more controllable while preserving the current BYOK privacy boundary and lightweight browser-extension architecture.

## Current Product Baseline

Current Aviso is still `v0.1 internal dogfood / 内部试用版`.

- Chrome MV3 extension.
- Plasmo remains the default build path today.
- WXT exists as a parallel build path only.
- Current usable model remains BYOK direct-provider.
- API keys stay in `chrome.storage.local/contextai_api_keys`.
- Non-secret settings stay in `chrome.storage.sync/contextai_settings`.
- Current provider baseline includes OpenAI, Anthropic, Doubao / Volcengine Ark, DeepSeek, Kimi / Moonshot, OpenRouter, Gemini, and Tencent Hunyuan as BYOK direct-provider configuration support.
- Current v0.2 implementation evidence must not be written as release ready.

## Global Boundaries

The following stay out of v0.2:

- No Aviso backend.
- No provider proxy.
- No login, subscription, payment, or anonymous quota.
- No telemetry, analytics SDK, or remote logs.
- No custom base URL in the current preset line.
- No automatic provider model-list fetching.
- No writing configuration support as live validation.
- No writing implementation support as release ready.

## Current Requirement Baseline

### v0.2.0 WXT migration / build-chain cleanup

Goal:

Establish a more stable extension build path for later provider and command-palette work.

In scope:

- Keep Plasmo default and rollback path.
- Keep WXT as a parallel build path.
- Confirm manifest parity.
- Confirm normal permissions, host permissions, commands, popup, content scripts, and locales are not accidentally changed.
- Close loaded-extension QA across Popup, AI service config, context menu, selection toolbar, command palette, clipboard toast, double-click menu, iframe, screenshot right-click internal path, and readability/page summary.

Out of scope:

- No direct switch to WXT default build.
- No deletion of Plasmo.
- No new permissions.
- No provider live validation.

Acceptance baseline:

- `npm run build:wxt` passes.
- Manifest parity passes.
- Loaded-extension QA has an explicit record.
- Current v0.2 keeps Plasmo as the default build path; WXT default-build migration belongs to a separate `v0.2.1` slice.

### Current v0.2 Speed baseline + fast-model strategy

Goal:

Make Aviso feel faster while keeping later performance claims verifiable and honest.

In scope:

- Immediate visible feedback after trigger.
- Slow responses show provider-waiting / processing states.
- No fake model output.
- Summary-only TTFT method.
- Fast-model strategy for short tasks such as translate / explain / polish, using the user's configured fast model when present.
- Long-context tasks such as page summary may keep using the default model.
- No automatic random model switching when no fast model is configured.

Out of scope:

- No telemetry.
- No remote performance collection.
- No unverified p50 / p95 claims.
- No live TTFT sampling for current v0.2 wording.
- No reasoning/thinking UI or request-parameter control in current v0.2.
- No privacy-boundary tradeoff for speed.

Acceptance baseline:

- Waiting state is visible.
- Fast-model strategy has explicit config behavior and fallback behavior.
- TTFT remains summary-only; current v0.2 does not write p50 / p95 values.
- Reasoning/thinking request-parameter control is removed from current v0.2 scope. It is not an active delivery item, postponed requirement, or wording prerequisite.

### v0.2.2 Provider expansion

Goal:

Support more mainstream model vendors while keeping Chrome permissions and privacy boundaries controlled.

Current provider set in implementation candidate:

- OpenAI
- Anthropic
- Doubao / Volcengine Ark
- DeepSeek
- Kimi / Moonshot
- OpenRouter
- Gemini
- Tencent Hunyuan

Recommended next batch for separate follow-up issues:

- Qwen / DashScope
- Zhipu GLM

In scope:

- User chooses a provider preset when adding an AI service.
- User fills API key, model ID, and display name.
- Clicking save accepts draft configuration even before a connectivity test succeeds.
- Saved state may remain `untested`, `unreachable`, or `needs configuration`.
- Users can continue editing.
- Saving after clearing API key must remove the old local key.
- OpenAI-compatible shared adapter is preferred where practical.
- Each provider still uses a fixed preset, fixed base URL, and fixed host permission.
- OpenRouter is an aggregator preset and must not be presented as equivalent to all vendor-direct support.
- Connectivity test remains manual, one provider config at a time, fixed public short prompt only, no webpage content, screenshot, URL, clipboard, or history payload, and summary-only redacted output.

Out of scope:

- No custom base URL.
- No arbitrary provider host input.
- No optional host permission flow in the current line.
- No automatic provider model-list fetching.
- No live validation claim from configuration support.

Acceptance baseline:

- Provider dropdown contains the approved target presets for the active batch.
- Registry, routing, connectivity, storage, i18n, and tests are covered at implementation time.
- Host permissions stay limited to explicitly approved provider hosts.
- API keys do not move into sync.
- Empty model ID blocks provider requests.
- No model-list fetching is added.
- Live validation remains a separate, authorized-only layer.

### v0.2.3 Command palette local intent enhancement

Goal:

Make the command palette feel like a local control surface without turning Aviso into an autonomous browsing agent.

In scope:

- Local history search.
- Local bookmark search.
- Local Aviso AI conversation search.
- Open URL candidate.
- Translate current page.
- Summarize current page.
- Ask AI directly.
- All open, navigation, and page actions remain confirm-first.

Out of scope:

- No web search.
- No autonomous browsing.
- No remote link-body fetching.
- No automatic sending of history, bookmarks, or full URLs to a provider.
- No new browser permissions.

Acceptance baseline:

- Search candidates come from local data only.
- Dangerous URLs are blocked.
- Open/page actions run only after explicit user selection.
- Local conversation restore does not re-send a provider request.
- Loaded-extension QA covers real command-palette interaction.
