# Aviso v0.2 Provider Architecture Preflight

Status: Draft / owner review
Updated: 2026-06-11
Scope: Docs-only architecture preflight for V02-001. No source code, manifest, dependency, storage-key, README, STATUS, RELEASE_CHECKLIST, backend, proxy, telemetry, web search, or provider-call change is approved by this document.

## Executive Summary

Aviso's provider architecture is a BYOK direct-provider Chrome MV3 extension path. At the time of this V02-001 preflight, source supported only three provider ids: `openai`, `anthropic`, and `doubao`. Current implementation status is tracked in `docs/archive/v0.2/v0.2-status.md`; later implementation added DeepSeek, Kimi / Moonshot, OpenRouter, Gemini, and Tencent Hunyuan configuration support without live provider validation.

At that time, approved host permissions were exactly:

- `https://api.openai.com/*`
- `https://api.anthropic.com/*`
- `https://ark.cn-beijing.volces.com/*`

The recommended v0.2 provider expansion path is:

1. Keep the current `contextai_*` storage namespace and current local-only API key boundary.
2. Separate `OpenAI-compatible` providers from `native` providers at the adapter contract level.
3. Defer custom user-provided base URLs until optional host permission design is separately approved.
4. Start implementation with a small OpenAI-compatible direct-provider batch after V02-002, V02-003, WXT migration parity, and exact host-permission approval.

## Current Repo Baseline

Current provider implementation:

- `ProviderId` is `openai | anthropic | doubao`.
- `ProviderSdk` is `openai | anthropic | openai-compatible`.
- `doubao` uses OpenAI-compatible routing with `DOUBAO_BASE_URL = https://ark.cn-beijing.volces.com/api/v3`.
- `src/background/ai-client.ts` has two concrete call paths: `callOpenAI` and `callAnthropic`.
- OpenAI-compatible calls reuse the OpenAI SDK with an optional `baseURL`.
- Provider connectivity tests are manual, one provider config at a time, fixed-prompt, and summarized through redacted fields.
- Popup provider config already supports multiple configs, manual model ID entry, default config selection, masked key display, and last connectivity status.

Current storage baseline:

- API keys stay in `chrome.storage.local/contextai_api_keys`.
- Legacy keys remain `{ openai, anthropic, doubao }`.
- New per-config keys stay under `contextai_api_keys.providerConfigKeys[configId]`.
- Non-secret settings stay in `chrome.storage.sync/contextai_settings`.
- Current provider config metadata lives in `contextai_settings.providerConfigs` and `contextai_settings.defaultProviderConfigId`.
- No `aviso_*` storage migration is approved.

## Capability Flag Legend

Capability flags below describe adapter contract planning, not shipped behavior.

- `textChat`: provider can accept normal text chat/completion requests.
- `streaming`: provider has a documented or current streaming path. Non-streaming providers must not fake streaming.
- `vision`: provider/model can accept image input; still model-dependent unless current repo validates a concrete model.
- `reasoningControl`: provider/model exposes explicit thinking/reasoning controls. v0.2 may gate this later; it is not currently implemented.
- `toolUse`: intentionally out of scope for v0.2 even when a provider supports tool calling.

## Adapter Contract Recommendation

### OpenAI-Compatible Adapter

Use this route for providers with an official OpenAI-compatible chat completion endpoint and a stable host permission decision.

Recommended contract fields:

- `providerId`
- `displayName`
- `sdk: "openai-compatible"`
- `hostPermission`
- `baseURL`
- `defaultModel`
- `requiresEndpointConfig`
- `capabilities`
- `modelIdMode: "manual"`
- `authMode: "bearer-api-key"`
- `streamingMode: "openai-chat-delta"`
- `errorCategoryMapper`
- `connectivityTestModel`

Behavior rules:

- Reuse the current OpenAI SDK `baseURL` pattern where conformance is verified.
- Keep manual model ID entry; do not call list-models APIs.
- Keep manual connectivity tests fixed-prompt and one provider config at a time.
- Normalize stream chunks into the existing `{ text, done }` shape.
- Do not fake streaming if a provider only supports non-streaming.
- Gate `vision`, `reasoningControl`, and `toolUse` by provider and model metadata; never infer them from provider name alone.
- Keep provider copy at "supports configuration" unless live validation evidence exists.

### Native Provider Adapter

Use this route only when a provider cannot safely use the OpenAI-compatible adapter or when official docs require provider-specific payloads, stream parsing, auth, signing, or SDK behavior.

Recommended contract fields:

- `providerId`
- `displayName`
- `sdk: "native"`
- `hostPermission`
- `clientFactory`
- `buildTextRequest`
- `buildVisionRequest`
- `streamParser`
- `errorCategoryMapper`
- `capabilities`
- `connectivityTestModel`
- `redactionPolicy`

Behavior rules:

- Native providers need a V02-005 spike before production implementation.
- New SDK dependencies are a stop line and need owner approval.
- Native streaming must be parsed into the same `{ text, done }` result contract.
- Native image input must pass the current screenshot/base64 privacy boundary and provider/model capability gates.
- Native signed APIs, OAuth, backend signing, or server proxy requirements are not v0.2 implementation scope without a new owner decision.

### Custom Endpoint Contract

Do not include arbitrary user-provided base URLs in the first implementation slice.

Reason:

- Chrome host permissions cannot safely cover arbitrary custom endpoints without a separate permission model.
- `<all_urls>` or broad wildcard permissions are out of scope.
- Optional host permissions and custom endpoint UI need their own design, risk review, and release gate.

## Storage Compatibility Note

V02-001 recommends preserving the current storage layout exactly:

- Keep API keys under `chrome.storage.local/contextai_api_keys`.
- Keep legacy provider key fields for existing users: `openai`, `anthropic`, `doubao`.
- Keep per-config API keys under `contextai_api_keys.providerConfigKeys[configId]`.
- Keep non-secret provider metadata under `chrome.storage.sync/contextai_settings`.
- Keep `providerConfigs` and `defaultProviderConfigId` in `contextai_settings`.
- Do not migrate to `aviso_*` keys.
- Do not store API keys, raw prompts, raw provider responses, private page text, screenshots/base64, full URLs, or clipboard content in docs, logs, sync storage, telemetry, or release artifacts.

Provider expansion should add provider metadata and route fields without changing the storage namespace or secret-storage location.

## Recommended First Implementation Slice

Recommended first implementation slice after V02-002, V02-003, WXT migration parity, and owner host-permission approval:

`V02-004A OpenAI-compatible direct-provider presets`

Scope:

- Add the generalized OpenAI-compatible provider metadata contract.
- Implement only a small direct-provider batch, not every candidate.
- Recommended first batch: `DeepSeek` + `Kimi / Moonshot`.
- Optional add-on if owner wants one aggregator in the first slice: `OpenRouter`.
- Optional add-on if owner chooses a single region: `Qwen / DashScope` with only `https://dashscope.aliyuncs.com/*`.

Why this slice:

- It reuses the current OpenAI-compatible `baseURL` route.
- It does not require native SDK dependencies.
- It keeps the UI model as manual model ID entry.
- It tests the smallest meaningful manifest expansion before adding many providers.
- It keeps Google Gemini, Tencent Hunyuan, Mistral conformance, Baidu Qianfan, native adapters, reasoning controls, and custom endpoints out of the first implementation pass.

Acceptance for this first slice should include:

- `git diff --check`
- `npm test`
- `npx tsc --noEmit`
- `npm run build`
- Manifest before/after host-permission review
- Unit tests for provider registry, config validation, route resolution, host permission equality, and unsupported capability gating
- Loaded-extension smoke check for Popup provider settings
- No execution-agent live provider calls

## Risks

- Host permission expansion is a release-risk item and may affect Chrome Web Store review.
- OpenAI-compatible does not mean identical behavior across streaming, error shape, image input, reasoning controls, or tool calling.
- Provider model catalogs change; Aviso must not fetch account model lists in v0.2.
- Aggregator providers such as OpenRouter can obscure true model capabilities; copy must remain "supports configuration" until validation exists.
- Regional provider hosts such as DashScope need exact owner decisions; adding multiple regions increases manifest scope.
- Native providers may require SDK dependencies, signed requests, or provider-specific stream parsing.
- Reasoning controls can improve speed only where a model/provider exposes documented controls; otherwise UI should show processing state rather than claiming latency is solved.
- WXT migration is listed as a required infrastructure track before provider implementation starts; provider source work should not outrun that parity gate.
- Baidu Qianfan remains unverified in this pass and should not enter implementation planning until official docs confirm endpoint and compatibility.

## Stop Lines

Stop before implementation or ask owner approval if any thread needs:

- New or changed `package.json` manifest permissions.
- New provider host permissions.
- Broad wildcard permissions, `<all_urls>`, or arbitrary custom endpoint access.
- API key storage migration or new secret-storage location.
- Reading, printing, logging, or documenting API keys.
- Real provider calls by the execution agent.
- Raw prompt, raw response, private page text, screenshots/base64, full URLs, or clipboard content in logs/docs/artifacts.
- Backend, proxy, hosted Aviso AI, account, login, subscription, payment, quota, telemetry, analytics, remote link fetching, or web search.
- New provider SDK dependencies.
- Public website/store claims that candidate providers are implemented or live validated.
- Implementation before WXT migration parity is accepted, if the implementation touches shared runtime/build files.
